这篇原创示例稿从一个常见场景开始：给手机导航做一个菜单按钮。图标很容易画出来，交互的语义却需要认真安排。

## 用元素表达操作的意思

导航到另一个页面，用链接；改变当前页面状态，用按钮。原生元素已经具备键盘行为，不必从一个可点击的 `div` 重新拼装。

```html
<button
  type="button"
  aria-label="打开导航"
  aria-controls="mobile-nav"
  aria-expanded="false"
>
  <!-- 图标只负责外观，按钮的名字由 aria-label 提供 -->
  <svg aria-hidden="true" viewBox="0 0 24 24"></svg>
</button>
<nav id="mobile-nav" aria-label="移动导航" hidden></nav>
```

展开后同步修改 `aria-expanded`，并移除导航的 `hidden`。可见状态与辅助技术读到的状态需要一致。不要只改变透明度，让看不见的链接仍然留在 Tab 顺序里。

## 让焦点始终有位置

焦点可见性是键盘使用者的定位线索。不要因为默认轮廓“不够好看”就直接移除它。可以用主题色重画，并保留与背景的清晰对比。

```css
:focus-visible {
  outline: 3px solid var(--primary);
  outline-offset: 5px;
}
```

如果焦点进入了弹窗，就应该暂时留在弹窗内部。关闭后，回到打开它的按钮。原生 `dialog` 能处理许多基础行为，但仍应在实际浏览器里检查。

### 避免焦点被页面更新吞掉

筛选文章时，最好让焦点停在触发筛选的按钮上，而不是直接跳到结果第一项。结果数量可以通过礼貌播报区域告知读者，不必打断正在进行的键盘操作。

## 状态不能只靠一种颜色

选中主题筛选项时，可以同时使用背景变化、对勾与 `aria-pressed`。对勾服务于视觉，属性服务于语义。让两者描述同一个状态，而不是各自维护一套逻辑。

还要注意点击区域。图标画得小，不代表按钮也必须很小。给图标外围留出足够空间，手指才能更容易点中。

## 一条五分钟检查路线

1. 放下鼠标，从地址栏按 Tab 进入页面。
2. 找到“跳到主要内容”链接并使用它。
3. 打开移动菜单，用 Escape 收起。
4. 打开搜索，输入“无障碍”，再关闭。
5. 把系统设置为减少动态效果，观察页面是否安静下来。

这条路线不能替代完整的无障碍审核，但能很快暴露明显阻碍。把它放进日常开发过程，比在最后才集中补救更容易。
